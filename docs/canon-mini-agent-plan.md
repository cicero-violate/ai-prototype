# Canon Mini Agent Plan

## Goal

Build a small local agent that uses a frontier model for planning, routing, constraint-setting, and verification while using the local model for bounded execution.

The system should perform runtime delegation only. It should not train, fine-tune, reinforce, or distill the local model from ChatGPT/frontier-model outputs unless the data is owned, licensed, and permitted for that purpose.

## Core Instruction

Convert each user goal into clear, bounded execution instructions for the local model.

The frontier model should:

1. Understand the user goal.
2. Produce a concise execution plan.
3. Define the local model's task, inputs, constraints, and success criteria.
4. Send only the bounded execution instruction to the local model.
5. Review the local model's output.
6. Correct, reject, retry, or finalize based on verification.

The local model should:

1. Execute only the assigned bounded task.
2. Avoid expanding scope unless explicitly instructed.
3. Return structured output.
4. Surface uncertainty, missing inputs, or execution failures.
5. Avoid claiming that it performed actions it did not perform.

## Runtime Flow

```text
User Goal
  -> Frontier Planner
  -> Bounded Local Instruction
  -> Local Model Executor
  -> Frontier Verifier
  -> Final Response
```

Symbolically:

```text
p = F(x)
y = L(x, p)
v = F(x, p, y)
```

Where:

- `x` is the user goal.
- `F` is the frontier model.
- `L` is the local model.
- `p` is the bounded instruction.
- `y` is the local output.
- `v` is the verification result.

## Frontier Model Responsibilities

The frontier model acts as planner, router, constraint setter, and verifier.

It should produce local-model instructions with this structure:

```text
TASK:
Describe the exact task the local model must perform.

INPUTS:
List all relevant input data, files, code, user constraints, and assumptions.

OUTPUT FORMAT:
Specify the exact output shape expected from the local model.

CONSTRAINTS:
State limits, safety boundaries, style requirements, and scope boundaries.

SUCCESS CRITERIA:
Define how the result will be judged.

FAILURE HANDLING:
State what the local model should do if the task cannot be completed.
```

## Local Model Responsibilities

The local model executes the assigned task and returns only the requested output.

It should not:

- Rewrite the user goal.
- Invent missing file contents.
- Claim tool execution without evidence.
- Train itself from frontier-model messages.
- Store frontier-model outputs for model development.
- Expand beyond the provided instruction.

It should:

- Follow the provided task exactly.
- Return concise, structured results.
- Mark uncertainty clearly.
- Ask for missing data only when execution is blocked.
- Prefer deterministic, reproducible steps.

## Verification

After local execution, the frontier model verifies the output against the original goal and the bounded instruction.

Verification checklist:

1. Does the output answer the user goal?
2. Does it follow the requested format?
3. Does it stay within scope?
4. Are claims supported by available inputs or tool results?
5. Are there hallucinated files, commands, outputs, or facts?
6. Are safety and compliance boundaries respected?
7. Is a retry needed with tighter instructions?

Verification result format:

```text
STATUS: pass | retry | reject
REASON: concise explanation
NEXT_ACTION: finalize | send_retry_instruction | ask_user | stop
```

## Data and Training Policy

Runtime logs may be used for debugging, observability, and evaluation.

Do not use ChatGPT/frontier-model outputs to train, fine-tune, reinforce, or distill a competing local model unless the data is owned, licensed, and explicitly permitted for that purpose.

Allowed data sources for local-model improvement:

- Human-written examples.
- User-owned datasets.
- Licensed datasets.
- Open datasets with compatible terms.
- Synthetic data generated by models or tools that permit model training.
- System telemetry that does not contain restricted frontier-model outputs.
- Human preference labels created independently.

Preferred improvement path:

1. Build evals first.
2. Collect human-authored examples.
3. Run supervised fine-tuning on permitted data.
4. Add preference data using permitted comparisons.
5. Use reinforcement learning only after evals are stable and reward hacking risks are controlled.

## Logging Policy

Save enough information to debug and evaluate the agent, but separate runtime orchestration logs from model-training data.

Recommended log fields:

```json
{
  "request_id": "string",
  "timestamp": "ISO-8601",
  "user_goal_summary": "string",
  "frontier_instruction_hash": "string",
  "local_instruction": "string",
  "local_output": "string",
  "verification_status": "pass | retry | reject",
  "verification_reason": "string",
  "final_response_summary": "string",
  "training_allowed": false
}
```

Do not mark logs as `training_allowed: true` unless every included field is permitted for model training.

## Retry Policy

Retry local execution when the output is incomplete, malformed, off-scope, unsupported, or unsafe.

Retry instruction template:

```text
The previous output failed verification for this reason:
<reason>

Retry the task with these stricter requirements:
<requirements>

Return only:
<expected output format>
```

Stop retrying when:

- The local model cannot complete the task after a small fixed number of attempts.
- Required inputs are missing.
- The task requires tools unavailable to the local model.
- The task would violate safety or compliance boundaries.

## Example Local Instruction

```text
TASK:
Summarize the provided file contents into implementation steps.

INPUTS:
- User goal: update the mini-agent plan.
- File content: provided in the task payload.

OUTPUT FORMAT:
Return markdown with sections: Goal, Runtime Flow, Responsibilities, Verification, Data Policy, Logging, Retry Policy.

CONSTRAINTS:
- Do not propose training on frontier-model outputs.
- Do not invent files or commands.
- Keep instructions operational and implementation-focused.

SUCCESS CRITERIA:
- The plan clearly separates runtime delegation from model training.
- The local model role is executor only.
- The frontier model role is planner and verifier.

FAILURE HANDLING:
If file content is missing, return: "BLOCKED: file content required."
```

## Implementation Priorities

1. Implement the planner prompt.
2. Implement the local instruction schema.
3. Implement local execution.
4. Implement verification.
5. Implement retry handling.
6. Implement logging with `training_allowed: false` by default.
7. Implement evals before any model-improvement loop.

## Non-Goals

- Do not build an automatic ChatGPT-output scraper.
- Do not train the local model on frontier-model outputs.
- Do not hide frontier-model involvement from users or logs.
- Do not treat orchestration logs as training data by default.
- Do not let the local model self-modify or expand task scope.

## Final Operating Rule

Use the frontier model to decide what should happen.
Use the local model to perform bounded execution.
Use verification before returning results.
Use only permitted data for training.
